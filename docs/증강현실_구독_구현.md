# 증강현실 · 구독 구현 정리

너두! 도레미! 앱에 들어간 두 축, **증강현실(AR) 손 추적 건반**과 **구독 결제**의
구현 상태를 한 곳에 정리한 문서다. 코드가 왜 그렇게 생겼는지(설계 의도)와,
아직 남아 있는 것을 함께 적는다.

- 대상 기준: `codex/firebase-auth-signup` 브랜치
- 관련 코드: `lib/space/`, `lib/pages/space_page.dart`, `android/hand_tracking/`,
  `lib/subscription/`, `functions/`

---

## 1. 증강현실 (AR)

### 1.1 두 가지 AR 모드

홈 → 2단계에서 `ArModePage`가 두 갈래를 보여준다.

| 모드 | 화면 | 구현 | 하는 일 |
| --- | --- | --- | --- |
| **톡톡 Lite** | `LessonFlowPage(cameraMode: true)` | 완료 | 카메라 미리보기를 배경으로 깔고, 기존 화면 터치 건반으로 한 음을 익힌다. 손 추적은 쓰지 않는다. |
| **톡톡 Space** | `SpacePage` | 1단계(Android) | 카메라가 실제 손을 추적해, 손가락 위치와 동작만으로 건반을 친다. |

Lite는 "AR처럼 보이는" 모드이고, Space가 실제 손 추적 모드다. 아래 내용은 전부
Space에 대한 것이다.

### 1.2 계층 구조

판정 규칙은 **Dart 한 곳**에만 둔다. 네이티브는 "손이 어디 있는지"만 답하고,
"어느 건반인지 / 눌렀는지"는 판단하지 않는다. 이래야 나중에 iOS를 붙여도 두
플랫폼의 연주감이 갈라지지 않는다.

```
SpacePage                 화면 · 미리보기 · 디버그 패널
  └─ SpaceController      카메라 프레임 흐름 관리, 소리 재생
       ├─ HandTrackerAdapter (interface)
       │    └─ AndroidHandTracker  MethodChannel('doremi/hand_tracking')
       │         └─ MainActivity.kt
       │              └─ HandTracker.java  (:hand_tracking 모듈)
       │                   └─ MediaPipe Hand Landmarker
       └─ KeyHitDetector   ← 순수 로직. 카메라도 Flutter도 모른다. 테스트는 여기.
```

### 1.3 네이티브 모듈 (`android/hand_tracking`)

- 별도 Android 라이브러리 모듈(`:hand_tracking`)로 분리하고, `app` 모듈이
  `implementation(project(":hand_tracking"))`으로 가져다 쓴다.
- **Kotlin이 아니라 Java로 썼다.** Flutter가 Built-in Kotlin으로 옮겨가면서
  하위 모듈이 Kotlin Gradle Plugin을 직접 적용하면 앞으로 빌드가 깨진다.
  이 코드에는 Kotlin 문법이 필요 없어서 의존을 없애는 쪽을 택했다.
- 모델: `src/main/assets/hand_landmarker.task` (MediaPipe, 약 7.8MB).
  `.task`는 압축되면 MediaPipe가 열지 못하므로 `noCompress += "task"`가 필수다.
- MediaPipe 버전(`tasks-vision:1.0.0`)은 **고정**한다. 추적 동작이 바뀌면
  아래 판정 파라미터를 전부 다시 맞춰야 한다.
- `minSdk`를 24로 올렸다 (`android/app/build.gradle.kts`).

`HandTracker.detect()`가 하는 일:

1. NV21 바이트 → ARGB 비트맵 직접 변환 (JPEG 인코딩 경로를 피한다)
2. 지정된 각도로 회전 + 좌우 반전
3. `RunningMode.VIDEO`, `numHands = 1`로 추론 (동기 호출 + 프레임 간 추적 유지)
4. 21개 랜드마크(x, y 정규화 좌표), `span`, `confidence` 반환

> **주의** — Java API에는 프레임별 랜드마크 신뢰도가 없어서 `confidence`에
> handedness(왼손/오른손 확신도) 점수를 대신 넣는다. 손이 가려지면 같이
> 떨어지므로 품질 지표로는 쓸 만하지만 진짜 게이트는 아니다. 실제 게이트는
> `HandLandmarkerOptions`의 `minHandDetection/Presence/Tracking = 0.4`다.
> iOS Vision은 관절별 실제 신뢰도를 주므로 그쪽에서 제대로 채운다.

### 1.4 MethodChannel 계약

채널 이름: `doremi/hand_tracking`

| 메서드 | 인자 | 반환 |
| --- | --- | --- |
| `initialize` | 없음 | `true` / `init_failed` 오류 |
| `detect` | `bytes`(NV21), `width`, `height`, `rotation`, `mirror`, `timestampMs` | `{landmarks: Float32List(42), span, confidence}` 또는 `null` |
| `dispose` | 없음 | `null` |

`MainActivity`는 추론을 단일 워커 스레드에서 돌린다. 플랫폼 메인 스레드를 막으면
카메라 미리보기가 끊기기 때문이다. 앞 프레임이 아직 도는 중이면(`busy`) 새 요청은
`null`로 즉시 돌려보낸다 — 밀린 프레임을 처리해 봐야 지연만 쌓인다.

### 1.5 프레임 파이프라인

```
CameraController(front, ResolutionPreset.low, yuv420)
   → startImageStream
   → 60ms 스로틀(약 16fps) + 앞 프레임 처리 중이면 버림
   → YUV420_888 → NV21 변환 (Dart)
   → MethodChannel detect
   → KeyHitDetector.update() / .miss()
   → keyDown 이면 TonePlayer.playNote(notes[keyIndex])
```

16fps는 프레임이 Dart ↔ 네이티브를 왕복하는 비용을 감안한 값이다. 두 군데에서
프레임을 버린다(Dart의 `_busy`, 네이티브의 `busy`) — 어느 쪽이 밀리든 지연이
누적되지 않게 한다. 한 프레임 처리에 실패해도 조용히 넘기고 다음 프레임에서
회복한다.

### 1.6 좌표계와 회전 — 가장 많이 틀리는 부분

랜드마크는 **네이티브가 회전·반전을 적용한 뒤**의 이미지 기준 정규화 좌표다.
따라서 화면 미리보기도 **똑같은 순서(반전 → 회전)** 를 거쳐야 뼈대가 실제 손에
겹친다.

- 그래서 `CameraPreview`를 쓰지 않는다. `CameraPreview`는 자체 회전을 한 겹 더
  넣어서 두 좌표 공간이 어긋난다. 대신 `camera.buildPreview()`를 직접
  `Transform.scale(scaleX: -1)` → `RotatedBox`로 감싼다.
- 미리보기와 오버레이를 `orientedSize` 하나의 `SizedBox` 안에 같이 올리고
  `FittedBox(fit: BoxFit.contain)`으로 맞춘다. `cover`로 채우면 세로 프레임이
  가로 화면에 눌려 이미지의 3분의 1만 남는다 — 손이 프레임 어디에 잡히는지
  봐야 하므로 잘라내지 않는다.
- 회전값은 상수로 박지 않는다. 기기마다 센서 장착 각도가 다르고, 태블릿을
  거치대에서 뒤집으면 또 틀어진다. `sensorOrientation`과 기기 방향으로
  계산한다(전면은 더하고 후면은 뺀다 — CameraX와 같은 식).
- 자동 계산이 틀리는 기기를 위해 디버그 패널에서 `자동 → 0 → 90 → 180 → 270`
  순으로 돌려볼 수 있다. 미리보기와 오버레이가 같이 돌아가므로 어느 값에서도
  둘은 어긋나지 않는다.

### 1.7 판정 로직 (`KeyHitDetector`)

**핵심 제약**: 카메라가 손을 거의 수평으로 본다. 그래서 "손을 앞으로 미는 것"과
"손가락을 드는 것"이 화면상 둘 다 「위로」가 되어 구분되지 않는다.
해결책은 **축의 역할을 나누는 것** —

- **좌우(x)** 는 *어느 칸인지* 만 정한다.
- **상하(y)** 는 *눌렀는지* 만 정한다.

판정에는 손 전체가 아니라 **검지 끝(랜드마크 8) 한 점**만 쓴다. 손 전체를 쓰면
손바닥이 여러 칸에 걸쳐 오발음이 급증한다.

#### 칸 선택

- 가동 범위(`rangeStart`~`rangeEnd`)를 `keyCount`(기본 4칸 = 도레미파)로 나눈다.
- 이미 들어가 있는 칸에는 칸 폭의 10%만큼 여유(히스테리시스)를 준다. 경계에서
  칸이 깜빡이는 것을 막는다.

#### 누름 판정 — 두 경로

1. **하강 제스처(gesture)**: 최근 200ms 창에서 가장 높았던 지점 대비
   손 크기(`span`)의 20% 이상 내려오고, 속도가 초당 프레임 높이의 25% 이상.
   *손 크기 기준*이라 아이 손 크기와 카메라 거리에 자동으로 맞춰진다.
2. **체류(dwell)**: 같은 칸에 300ms 머무르면 발음.
   단, 「머무름」은 가만히 있는 것이지 지나가는 것이 아니다. 좌우 속도가 초당
   0.15를 넘으면 체류 시간을 다시 센다 — 이게 없으면 칸을 훑고 지나가는 동작이
   중간 칸을 전부 울린다.

두 경로를 모두 남겨 두고 `gestureHits` / `dwellHits`를 세고 있다. 실기기
테스트로 어느 쪽을 남길지 정한다.

#### 오발음 방지 장치

| 장치 | 동작 |
| --- | --- |
| 해제(release) | 누른 뒤 손 크기의 12%만큼 올라와야 재입력을 허용 |
| 쿨다운 | 같은 칸은 150ms 안에 다시 울리지 않음 |
| 버스트 제한 | 3초 안에 8회를 넘기면 잠시 발음을 멈춤 (소리가 다시 자극이 되는 되먹임 차단) |
| 신뢰도 하한 | `confidence < 0.5` 프레임은 손을 못 찾은 것으로 취급 |
| 평활 | 최근 3프레임 평균 (지연 약 180ms — 하강 창 200ms는 이보다 넉넉해야 한다) |
| 추적 손실 | 5프레임 연속 못 찾으면 눌린 칸을 놓고 keyUp |

#### 파라미터 (`HitConfig`)

```
keyCount 4     rangeStart 0.08    rangeEnd 0.92     boundarySlack 0.10
dwellMs 300    dwellMaxSpeed 0.15
descentWindowMs 200   descentSpanRatio 0.20   descentSpeed 0.25
releaseSpanRatio 0.12   cooldownMs 150   minConfidence 0.5
smoothing 3    lostFrames 5     burstLimit 8    burstWindowMs 3000
```

**전부 미검증 초기값이다.** 실기기에서 튜닝한 뒤 이 값들을 되써넣어야 한다.

### 1.8 테스트

`test/key_hit_detector_test.dart` — 카메라 없이 도는 순수 로직 테스트 14종.
특히 다음 두 개가 위 설계의 핵심을 지킨다.

- `칸 사이를 가로로 지나가도 중간 칸이 울리지 않는다` (dwellMaxSpeed)
- `손 전체가 앞으로 밀려도 하강으로 오인하지 않는다` (축 분리 + span 기준)

### 1.9 남아 있는 것

- **iOS 미구현.** `HandTrackerAdapter` 인터페이스만 있고 구현이 없다.
  `SpaceController`는 기본값으로 `AndroidHandTracker`를 만든다. iOS는 Vision
  프레임워크로 붙이면 되고, 판정 로직은 그대로 재사용된다.
- **캘리브레이션 미구현.** `HitConfig.copyWith`로 `rangeStart/End`를 덮어쓸
  자리는 만들어 뒀지만 아직 쓰는 곳이 없다. 아이 팔 길이에 맞춰 가동 범위를
  잡는 절차가 필요하다.
- **파라미터 실기기 튜닝**, **회전 기본값 확정**이 다음 단계다.
- 현재 Space는 4칸(도레미파)만 쓴다. `notes`는 8음까지 있다.

## 2. 구독 (인앱 결제)

### 2.1 정책

- 상품: 월간 구독 하나뿐. 상품 ID `doremi_premium_monthly`.
- 무료 체험: **14일**. 체험 중에는 구독 없이 모든 콘텐츠가 열린다.
- 잠기는 것: 홈의 학습 콘텐츠 3개(1·2·3단계). 잠긴 상태에서 누르면 구독 관리
  다이얼로그가 뜬다 (`_openPremiumContent`).
- 가격은 앱에 적지 않는다. 스토어가 알려 준 현지 통화 가격(`priceLabel`)만
  보여주고, 아직 못 받았으면 결제 버튼 자체를 막는다. 앱에 적어 두면 통화나
  인상된 가격이 어긋난다.

### 2.2 신뢰 경계 — 판정은 서버가 한다

앱은 권한을 **스스로 켜지 않는다.** 앱을 고쳐도 유료 잠금이 열리지 않게 하는
것이 이 구조의 목적이다.

```
스토어(Play / App Store)
      │ 영수증
      ▼
SubscriptionController ──verifyPurchase(callable)──▶ Cloud Functions
      ▲                                                   │ 스토어에 재확인
      │                                                   ▼
      └──── watchEntitlement (Firestore 실시간) ──── subscriptions/{uid}
```

Firestore 규칙(`firestore.rules`):

- `subscriptions/{uid}` — 본인만 **읽기**, 쓰기는 `false` (서버 Admin SDK만 기록)
- `purchaseReceipts/{fingerprint}` — 앱에서 읽지도 쓰지도 못함

`backend`가 `null`인 실행(Firebase가 붙지 않은 데모·테스트)에서만 스토어 응답만
보고 판단한다.

### 2.3 앱 쪽 (`lib/subscription/`)

| 파일 | 역할 |
| --- | --- |
| `subscription_controller.dart` | 스토어 연결, 구매·복원, 상태 노출 (`ChangeNotifier`) |
| `subscription_backend.dart` | 권한 판정 주체 인터페이스 + Firebase 구현 |
| `entitlement.dart` | 권한 상태 모델 + `accountTokenFor(uid)` |
| `trial_period.dart` | 14일 체험 계산, 체험 시작일 결정 |

주요 동작:

- **초기화**: 서버 권한 스트림 구독 → 스토어 가용성 확인 → 상품 정보 조회 →
  복원 스윕. 스토어가 응답했을 때만 권한을 다시 판정한다. 실패하면 캐시된
  권한이 그대로 유지된다.
- **복원 스윕**: `restorePurchases()`는 결과를 `purchaseStream`으로만 알려 준다.
  호출 뒤 3초(`restoreSettleDelay`) 동안 스트림을 지켜보고 판정한다.
  서버를 쓰는 경우 여기서 권한을 정하지 않고, 영수증을 서버로 넘기기만 한다.
- **보류 결제**(계좌이체·보호자 승인): 결과가 올 때까지 `purchasePending`을
  유지해 버튼이 다시 눌려 중복 결제되는 것을 막는다.
- **검증 실패**: 이미 가진 권한을 뺏지 않는다. 서버 스트림에서 다음 결과가 오면
  그때 맞춰진다.

#### 오프라인 유예 (7일)

비행기 모드나 서버 장애로 스토어에 연결하지 못하는 동안, 마지막으로 확인한
권한을 `SharedPreferences`에 남겨 두고 **7일까지** 인정한다. 그 뒤에는 다시
스토어 확인을 요구한다 — 결제한 사용자가 잠기지도, 해지한 사용자가 계속 쓰지도
않게 하는 절충이다. 캐시 키는 uid별로 분리한다 (`premium_subscribed_<uid>`).

#### 체험 시작일 결정

```dart
earliestTrialStart(기기_첫_실행일, 계정_생성일)  // 더 이른 쪽
```

- 기기 첫 실행 시각(`trial_started_at`)은 로그아웃·탈퇴로 지우지 않는다.
  → **탈퇴 후 재가입해도 같은 기기에서 체험이 다시 시작되지 않는다.**
- Firebase 계정 생성 시각은 비어 올 수 있다. 그때 컨트롤러를 만들지 않으면
  유료 콘텐츠가 통째로 열려 버리므로, 기기 시각으로 대체한다.
- 기기를 바꾼 기존 사용자는 계정 생성일이 더 이르므로 그대로 인정된다.

### 2.4 서버 쪽 (`functions/`)

배포 지역 `asia-northeast3` (앱의 `FirebaseSubscriptionBackend._region`과 반드시 일치).

**`verifyPurchase` (onCall)** 처리 순서:

1. 로그인 확인 (`request.auth.uid`)
2. 플랫폼 / 상품 ID / 영수증 유효성 검사 — 아는 상품 하나만 받는다
3. 스토어에 재확인 (Google Play API 또는 App Store Server API)
4. **구매자 식별자 대조** — 영수증에 남은 토큰이 `accountTokenFor(uid)`와 다르면 거부
5. **영수증 소유권 잠금** — `purchaseReceipts/{sha256(영수증)}`에 최초 사용자를
   트랜잭션으로 묶는다. 같은 영수증을 여러 계정이 돌려쓰지 못한다. 구매자
   식별자가 없는 예전 구매를 막는 최후의 방어선이다.
6. `subscriptions/{uid}`에 기록 → 앱의 실시간 스트림으로 흘러간다

#### 계정 식별자 (`accountTokenFor`)

`uid` → `sha256("doremi:<uid>")` 앞 16바이트 → RFC 4122 v5 형태 UUID.
결제할 때 스토어에 심어 두고(Android `obfuscatedAccountId` / iOS
`appAccountToken`), 서버가 같은 계산을 다시 해 영수증의 주인을 확인한다.
따로 저장할 필요가 없다.

> **Dart와 TypeScript 두 곳에 같은 계산이 있다.**
> `lib/subscription/entitlement.dart` ↔ `functions/src/entitlement.ts`
> 한쪽만 고치면 결제가 전부 거부된다.
> `test/subscription_server_verification_test.dart`의
> `서버(Node)와 같은 값을 만든다` 테스트가 이 일치를 지킨다.

#### 상태 매핑

| 스토어 상태 | 앱 상태 | 콘텐츠 |
| --- | --- | --- |
| Play `ACTIVE`, `CANCELED`(기간 남음) / App Store `1` | `active` | 열림 |
| Play `IN_GRACE_PERIOD` / App Store `4` | `grace` | **열림** (결제 유예 중에도 학습은 계속) |
| Play `ON_HOLD` / App Store `3` | `onHold` | 잠김 |
| Play `PAUSED` | `paused` | 잠김 |
| 그 외 / 만료 시각 경과 | `expired` | 잠김 |

상태가 활성이어도 만료 시각이 이미 지났으면 `expired`로 내린다.

#### 플랫폼별 확인 방법

- **Google Play**: `purchases.subscriptionsv2.get`. 서비스 계정 키 파일을 두지
  않고 함수 런타임의 기본 자격 증명을 쓴다. → Play Console에서
  `<projectId>@appspot.gserviceaccount.com`을 사용자로 초대하고
  "재무 데이터 보기" 권한을 줘야 한다.
- **App Store**: In-App Purchase 키(.p8)로 ES256 JWT를 만들어 Server API 호출.
  운영에서 못 찾으면 샌드박스로 다시 조회한다(테스터 계정 대응).
  JWS 서명은 검증하지 않는다 — 거기서 꺼내는 건 `transactionId`뿐이고, 실제
  판정은 Apple 서버 응답으로 한다. 응답에서 `bundleId`와 `productId`를 다시
  확인한다.

배포 전 필요한 시크릿:

```bash
firebase functions:secrets:set APP_STORE_KEY_ID
firebase functions:secrets:set APP_STORE_ISSUER_ID
firebase functions:secrets:set APP_STORE_PRIVATE_KEY
```

## 3. 두 기능의 접점

- Space 모드는 2단계 콘텐츠 아래에 있으므로 **구독·체험 권한이 있어야 진입**한다
  (`_openPremiumContent(RootPage.arModes)`).
- 둘 다 권한 요청이 필요하다 — AR은 카메라, 구독은 스토어 연결. 어느 쪽도
  실패를 조용히 넘기지 않고 화면에 이유를 표시한다.
